        """Execute task work unit and return output reference manifest."""

class TaskRegistry:
    def __init__(self):
        self._handlers: Dict[str, PipelineTaskHandler] = {}

    def register(self, handler: PipelineTaskHandler) -> None:
        self._handlers[handler.stage_name] = handler

    def get(self, stage_name: str) -> PipelineTaskHandler:
        if stage_name not in self._handlers:
            raise KeyError(f"No task handler registered for stage '{stage_name}'")
        return self._handlers[stage_name]

    async def execute_next_tasks(self, instance_id: str) -> None:
        async with self._session_factory() as session:
            pending_tasks = await self._get_ready_tasks(session, instance_id)
            for task in pending_tasks:
                await self._run_task(session, task)

    async def _run_task(self, session, task_row) -> None:
        handler = self._registry.get(task_row.stage_name)
        ctx = TaskContext(
            workflow_instance_id=str(task_row.workflow_instance_id),
            task_execution_id=str(task_row.id),
            document_id=str(task_row.document_id),
        )

        await self._mark_status(session, task_row.id, "RUNNING")
        try:
            inputs = await self._resolve_input_artifacts(session, task_row.input_ref)
            outputs = await handler.execute(ctx, inputs)
            await self._mark_completed(session, task_row.id, outputs)

### Core Conceptual Layers

1. **Instruction Manifest Layer (Meta Level)**
* **Goal:** Provide a declarative payload that configures the agent network without code changes.
* **Payload Components:**
* `Roles`: Specs for dynamic agents (e.g., Structure Extractor, Validator, Diff Engine, Concept Map Builder).
* `Graph Mechanics`: Routing dependencies (e.g., Sequential, Fan-Out/Fan-In, Conditional Loop until Validated).
* `Tool Binding`: Capabilities attached to agents (e.g., OCR, Sheet Parser, Embedder, DB Transaction Sink).
* `Schemas`: Input, Intermediate, and Output Pydantic/JSON schemas.




2. **Runtime Engine (Execution Level)**
* **Agent Coordinator:** Spawns specialized sub-agents based on the instruction manifest.
* **Shared Memory & State Graph:** Manages artifact state transitions, step-level idempotency, and intermediate evaluation context.
* **Tool Execution Boundary:** Sandboxed invocation of tools (parsing, computing diffs, generating embeddings).


3. **Specialized Sub-Flow Execution (Platform Level)**
* The framework processes the artifact, passes it through the instructed task graph, and materializes output into domain entities.

### Key Design Advantages of this Approach

* **Zero-Code Workflow Addition:** Adding Workflow C (e.g., Medical Records Ingestion) simply requires crafting `Instruction Set 3` mapping existing tool primitives to a new task graph.
* **Decoupled Intelligence from Determinism:** Deterministic tasks (tabular extraction, row-diffing, schema validation) remain handled by high-performance code tools, while non-deterministic tasks (semantic categorization, header layout interpretation, entity resolution) are delegated to instructed agents.
* **Symmetrical Diagnostics:** The runtime engine emits standard event traces regardless of platform, simplifying monitoring, cost/token management, and error recovery.

### Core Pipeline Components (Shared)

The generalized core framework handles execution control, metadata tracking, and persistence, leaving domain logic to extensible processor plugins.

* **Ingestion Adapter & Event Bus:** Standardizes incoming artifacts into a unified `IngestionPayload` containing source metadata, artifact hashes, raw payload pointers, and content MIME types.
* **Orchestration Engine:** Manator/State Machine execution tracking each stage (Queued, Processing, Enriched, Persisted, Failed) to ensure idempotent retries and granular observability.
* **Schema & Quality Guard:** Validates raw inputs against predefined baseline constraints (e.g., non-empty files, supported MIME types, file signature validation) prior to sub-flow routing.
* **Unified Persistence Layer:** Standardized abstraction layer for downstream storage:
* *Document Store:* Hierarchical/JSON documents (PostgreSQL / DocumentDB / MinIO).
* *Vector Store:* Embeddings for semantic retrieval (Qdrant / PGVector).
* *Relational Store:* Structured transactional records for catalog/entity sync.



---

### Core Workflow Lifecycle

1. **Ingest & Fingerprint:** The intake interface receives an artifact, assigns a deterministic tracking ID (SHA-256 content hash), and logs initial state in the tracking database.
2. **Dispatch:** Routing rules evaluate the payload type and header target to trigger the appropriate specialized sub-flow.
3. **Execute Sub-Flow:** The domain-specific pipeline processes, partitions, and enriches the input artifact into canonical objects.
4. **Reconcile & Store:** Output artifacts are validated against output schemas and atomically saved/upserted to target datastores.
5. **Notify & Complete:** Publish completion events with run metrics (tokens, execution time, record counts) to downstream subscribers.

### Specialized Sub-Flow Mechanics

#### Sub-Flow A: Document Processing Pipeline

*Target Artifacts: Unstructured PDFs, Scraped Web Content, Books, Markdown*

1. **Layout Parsing & Extraction:**
* Converts complex formats (PDF, images) using layout-aware engines to isolate structural blocks (headers, body, code blocks, figures).


2. **Hierarchical Document Tree Building:**
* Transforms flat parsed content into a parent-child AST (Abstract Syntax Tree) representing document sections, chapters, and nested headings.


3. **Semantic Partitioning & Chunking:**
* Splits document sections using structure-preserving algorithms (e.g., header-aware or sliding-window boundaries with context inheritance) to preserve contextual completeness.


4. **Enrichment & Embedding Generation:**
* Passes chunks to embedding services and LLM annotators for metadata tagging (keywords, concepts, summaries).


5. **Vector & Context Indexing:**
* Outputs indexed vector embeddings linked to the parent canonical document tree.



#### Sub-Flow B: Catalog Update Pipeline

*Target Artifacts: Structured/Semi-Structured Sheets (Excel, CSV, PDF Tables)*

1. **Tabular Extraction & Layout Normalization:**
* Extracts grid structures from multi-tab Excel workbooks or detects native table borders in unstructured PDFs.


2. **Schema Alignment & Mapping Engine:**
* Maps heterogeneous column headers (e.g., "SKU", "Prod_ID", "Item #") to standard enterprise catalog schemas via dynamic configuration or structured schema extraction.


3. **Entity Validation & Business Rule Audit:**
* Executes strict field-level type checking (e.g., numeric price limits, ISO currency codes, valid category IDs). Flags invalid rows for staging/human review.


4. **Delta & Diffing Engine:**
* Compares extracted records against the current database state to classify records into **Create**, **Update**, **Delete**, or **Unchanged** actions.


5. **Transactional Bulk Upsert:**
* Applies reconciled database updates within single transactional batches to maintain catalog state integrity.

To keep the core framework decoupled from individual file formats or execution logic, every processing step implements a standard component contract:

* `IngestorInterface`: Maps raw sources to standard bytes/streams with headers.
* `ParserInterface`: Consumes raw content and outputs normalized domain entities (Structured Tree or Staging Rows).
* `TransformerInterface`: Executes domain-specific enrichments, diffing, or embedding.
* `SinkInterface`: Handles destination-specific writing logic.

### Core Framework Pillars

The framework provides three fundamental meta-layers required to build any domain platform:

#### 1. Entity Meta-Model (Domain & Data Layer)

Defines enterprise domain models declaratively without writing manual schema migrations or entity boilerplate.

* **Universal Primitive Definition:** Defines entities, properties, data types, constraints, and relational mappings (1:1, 1:N, N:M).
* **Built-in Platform Core Entities:** Pre-baked universal entities available out of the box:
* `User / Auth Entity`: Identity, roles, access permissions, multi-tenancy boundaries.
* `Payment / Transaction Entity`: Subscriptions, invoices, ledgers, token processing.


* **Dynamic Schema Generation:** Compiles entity declarations into relational databases, document stores, or Pydantic validation objects at runtime.

#### 2. Workflow Meta-Model (Execution & Behavioral Layer)

Defines execution flows as Directed Acyclic Graphs (DAGs) composed of deterministic tools and autonomous agents.

* **Task Graph Specs:** Explicit sequence, concurrency, branching criteria, and error escalation hooks.
* **Tool & Agent Bindings:** Declarative binding of tools (Parsers, Calculators, Storage Sinks) and LLM Prompts to graph nodes.
* **State Machine Persistence:** Automatic DB tracking of step lifecycle (`PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `RETRYING`).

#### 3. Cross-Cutting Service Fabric

Core infrastructure exposed standard across all realized platforms:

* **Audit & Telemetry Log:** Standardized logging for LLM token metrics, runtime latencies, and transaction hashes.
* **Storage Bus:** Unified interface for Blob storage (S3/MinIO), Vector storage (Qdrant/PgVector), and Transactional SQL (PostgreSQL).
* **Agent Control Plane:** Machine-readable interface allowing triage agents to inspect, suspend, retry, or skip task steps.

### Core Framework Structural Breakdown

#### 1. Industry Meta-Repository

The central repository stores standard entity structures and base lifecycle state charts derived from open industry protocols (such as TM Forum, Schema.org, and ISO standards):

* **Meta-Entities:** Base templates for core enterprise domains (`PartyRole`, `ProductOffering`, `DigitalAsset`, `BillingAccount`).
* **Base Lifecycles:** Canonical state machine declarations for user activation, payment authorizations, subscription renewals, and inventory management.

#### 2. Entity Modeling Engine & Lifecycle State Machine

Every entity is bound to a formal Finite State Machine (FSM). Transition rules govern how an entity changes state in response to platform events or workflow execution outputs.

```
       [ Draft ]
           │
           ▼ (Validate & Enrol)
      [ Active ] ◄────────────────┐
           │                      │
           ├──► (Payment Failure) │ (Payment Recovered)
           │                      │
           ▼                      │
     [ Suspended ] ───────────────┘
           │
           ▼ (Cancellation / Expiry)
    [ Terminated ]

```

#### 3. Variant & Channel Resolution Layer

Business logic varies across lines of business (B2B vs. B2C) and sales channels (Direct, Marketplace, API). The workflow engine applies instruction overrides dynamically at runtime based on the incoming channel context.

#### Component 1: Entity Definition & Lifecycle Manifest (User & Payment Domain)

Entities declare their schema, underlying storage engine, and valid state transitions.

```yaml
entity: UserSubscriber
domain: IdentityManagement
industry_standard_ref: "TMForum:TMF629_Customer"

attributes:
  id: { type: uuid, primary_key: true }
  email: { type: string, required: true, unique: true }
  status: { type: string, default: "DRAFT" }
  channel_id: { type: string, required: true } # B2C_WEB, B2B_ENTERPRISE, DIRECT
  billing_account_id: { type: uuid, reference: BillingAccount.id }

lifecycle_fsm:
  initial_state: DRAFT
  states: [DRAFT, PENDING_VERIFICATION, ACTIVE, SUSPENDED, TERMINATED]
  transitions:
    - event: SUBMIT_VERIFICATION
      from: DRAFT
      to: PENDING_VERIFICATION
    - event: VERIFY_SUCCESS
      from: PENDING_VERIFICATION
      to: ACTIVE
    - event: PAYMENT_FAILED
      from: ACTIVE
      to: SUSPENDED
    - event: PAYMENT_RECOVERED
      from: SUSPENDED
      to: ACTIVE
    - event: CANCEL
      from: [ACTIVE, SUSPENDED]
      to: TERMINATED

```

#### Component 3: Instruction-Driven Task Graph (User Onboarding & Checkout)

The task graph defines execution sequences, agent tool bindings, and state mutation rules upon completion.

```yaml
workflow: UserOnboardingAndCheckout
version: 1.0
channel_context: "${input.channel_id}"

steps:
  - step_id: create_subscriber_record
    type: ENTITY_MUTATION
    action: CREATE
    target_entity: UserSubscriber
    input_mapping:
      email: "${input.email}"
      channel_id: "${input.channel_id}"
    outputs: [subscriber_id]

  - step_id: route_payment_processing
    type: CONDITIONAL_BRANCH
    condition: "${input.channel_id == 'B2B_ENTERPRISE'}"
    if_true: process_enterprise_invoice
    if_false: process_card_payment

  - step_id: process_card_payment
    type: TOOL_EXECUTION
    tool: PaymentGatewayAdapter
    inputs:
      amount: "${input.amount}"
      token: "${input.payment_token}"
    on_success:
      mutate_entity: UserSubscriber
      transition_event: VERIFY_SUCCESS
    on_failure:
      mutate_entity: UserSubscriber
      transition_event: PAYMENT_FAILED

  - step_id: process_enterprise_invoice
    type: AGENT_EXECUTION
    agent: CreditRiskVerificationAgent
    inputs:
      company_id: "${input.company_id}"
      requested_credit: "${input.amount}"
    on_success:
      mutate_entity: UserSubscriber
      transition_event: VERIFY_SUCCESS
```

### End-to-End Execution Flow

1. **Schema Initialization:** The core runtime compiles entity manifests (e.g., `UserSubscriber`, `PaymentTransaction`) from the Industry Meta-Repository, building Pydantic validators and database schemas.
2. **Event Trigger:** An incoming payload (e.g., a purchase request) carries a specific `channel_id`.
3. **Graph Compilation:** The runtime loads the corresponding `Workflow DAG` and applies channel-specific variant rules.
4. **State Machine Enforcement:** Steps execute deterministically or via AI agents. Step completion drives FSM state transitions on target entities.
5. **Agent Triage:** If a step fails (e.g., payment gateway failure, column mismatch), the execution state is written to `lp_task_executions`, and the Agent Control Plane triggers a triage agent to inspect, override, or retry the task node.

### Key Architectural Pillars

#### 1. Namespace Hierarchy & Polymorphic Inheritance Engine

Entities are scoped using explicit path namespaces (`<layer>/<domain>/<entity>`). Sub-namespaces inherit properties from parents and declare additions or overrides without mutating base definitions.

```yaml
# 1. Global Base Entity
namespace: "global/identity"
entity: "User"
attributes:
  id: { type: uuid, primary_key: true }
  first_name: { type: string, required: true }
  last_name: { type: string, required: true }
  contact_info: { type: jsonb }

# 2. Inherited Industry-Specific Customization
namespace: "industry/telecom/A_123"
entity: "User"
extends: "global/identity/User"

attributes:
  msisdn: { type: string, required: true, unique: true }
  service_account_id: { type: string }

lifecycle_fsm_override:
  states_added: [PROVISIONING_NETWORK, PORTING_IN]
```

#### 2. Synthesizer ("The Farming Unit") & Prompt Framework

* **Extraction System Prompt:** Forces LLMs to output syntactically valid YAML/JSON manifests adhering to our Meta-Model primitives.


* **Validation Guardrail:** Dynamic validation engine executes structural checks on generated manifests prior to namespace registration.

### Phased Implementation Strategy & Rollout Plan

To ensure continuous system reliability and avoid a risky "big bang" release, the framework will be delivered across four progressive phases:

```
 Phase 1: Static Engine ──► Phase 2: Inheritance ──► Phase 3: Generative LLM ──► Phase 4: Agent Loop
 (DB & Task Runner)        (Namespaces & FSM)       (Spec-to-Manifest)         (Self-Evolving)

```

#### Phase 1: Deterministic Engine & Core Schema Compiler

* **Goal:** Establish DB-backed state machines and standard execution handlers.


* **Deliverables:**
* Deploy core state tracking tables (`lp_workflow_definitions`, `lp_workflow_instances`, `lp_task_executions`).


* Implement static Pydantic/SQLAlchemy schema compiler for explicit YAML definitions.
* Shadow-write workflow steps alongside current legacy pipelines.





#### Phase 2: Namespace Registry & Inheritance Engine

* **Goal:** Enable polymorphic entity extensions and channel/LOB workflow variants.


* **Deliverables:**
* Build namespace resolution engine (`global` $\rightarrow$ `industry` $\rightarrow$ `custom`).
* Implement FSM lifecycle state machine transitions for entities.


* Realize initial **Learning Platform (LP)** and **Commerce Platform (CP)** base manifests.





#### Phase 3: Generative Spec Ingestion ("Meta-Builder Brain")

* **Goal:** Automate schema and workflow generation from raw documents, RFCs, and text instructions.
* **Deliverables:**
* Deploy LLM-driven Spec-to-Manifest transformation pipeline.
* Integrate validation guardrails and automated syntax checkers for synthesized YAMLs.
* Enable on-the-fly "ingredient farming" for custom industry domains.



#### Phase 4: Agent Control Plane & Self-Evolving Metaverse

* **Goal:** Expose control plane tools to autonomous triage agents for self-healing and dynamic platform execution.


* **Deliverables:**
* Expose manifest inspection, step retry, and DAG replanning APIs as agent tools.


* Automate failure escalation and parameter tuning via operational triage loops.
