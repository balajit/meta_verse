Co-Architect Architectural Review & Gap Remediation
The architecture is substantially more mature than the earlier iterations: it now has explicit authority boundaries, immutable artifacts, governance gates, durable build state, tenant isolation, CAS integrity, and recovery semantics.
However, there are several cross-section inconsistencies and unresolved distributed-systems contracts that should be corrected before implementation. The most important issue is that some later architectural decisions supersede earlier sections, but the earlier sections have not yet been normalized. That creates ambiguity for implementers.

I recommend treating the following as the Architecture Review Action Register, with each item explicitly mapped to the section where it should be applied.

1. Section 2.1 — Boundary Architecture: Plane Model Is Internally Inconsistent
Gap
The document states that the architecture has a Five-Plane Model, but then enumerates:
Experience
Control / Orchestration
Governance
Registry
Compilation
Persistence
That is six planes.
Additionally, the diagrams still effectively describe a boundary plane plus internal state plane rather than the later six-plane architecture.

Risk
Different implementation teams could interpret service placement differently.
For example:

Is API Gateway part of Experience or Control?
Is OPA its own plane or part of Governance?
Is PostgreSQL part of Persistence only?
Does BCR belong to Registry or Internal State?
Solution
Rename this explicitly to:
Six-Plane Architecture
and establish authoritative ownership:
Plane	Primary responsibility
Experience	REST API, CLI, external request contracts
Control / Orchestration	Job lifecycle, queue, workers, leases, cancellation
Governance	Authentication context, OPA, validation, policy enforcement
Registry	BCR, URN resolution, lifecycle, lineage authority
Compilation	meta_builder, meta_builder_brain, meta_polymorph, meta_compiler
Persistence	PostgreSQL, CAS, audit/WORM projection

Apply to
Section 2.1 — replace the current two-plane conceptual model with the six-plane model.
Also update the high-level architecture diagram so that the diagram and prose use the same plane terminology.

2. Section 2.2 — Component Responsibility Matrix: Ownership Boundaries Need to Be Made Authoritative
Gap
There are several overlapping responsibilities.
For example, earlier sections describe:

BCR as authoritative for specifications.
PostgreSQL specifications_registry as a persistent specification store.
meta_builder as authoritative for build state.
CAS as authoritative for artifact content.
But it is not yet obvious whether specifications_registry is:
a cache,
a projection,
a BCR implementation detail,
or an independent registry.
Risk
This is a classic split-brain source-of-truth problem.
An implementation could modify:

PostgreSQL.specifications_registry

without modifying BCR, creating:
BCR -> ACTIVE version A
PostgreSQL -> ACTIVE version B

Solution
Introduce an explicit Authority Matrix.
Proposed addition to Section 2.2
Data Object	Authoritative System	Consumer/Cache	Mutation Owner
Blueprint manifest	BCR	PostgreSQL projection/cache	BCR
Blueprint lifecycle	BCR	PostgreSQL projection	BCR
URN → CAS mapping	BCR	PostgreSQL projection	BCR
CAS blob	CAS	None	CAS writer
Build state	meta_builder PostgreSQL	Redis/UI caches	Build orchestrator
Build events	meta_builder PostgreSQL + WORM anchor	Search/log systems	Event writer
Artifact manifest	BCR	meta_builder projection	BCR
Build reproducibility manifest	meta_builder	BCR reference	Build orchestrator

Then explicitly state:
specifications_registry is a projection/cache of BCR state, not an independent specification authority.
If the intention instead is for PostgreSQL to implement BCR, that needs to be stated explicitly and the architectural distinction removed.
3. Section 3.1 — Specification Management Interface: Request Idempotency Is Underspecified
Gap
Section 3.5 requires:
Idempotency-Key: UUID

but Section 3.1 does not define the persistence model for it.
Risk
A retry can produce duplicate jobs if the API process crashes after job creation but before returning the response.
Solution
Add an idempotency table.
CREATE TABLE build_idempotency_keys (
    tenant_id UUID NOT NULL,
    idempotency_key VARCHAR(255) NOT NULL,
    request_sha256 CHAR(64) NOT NULL,
    job_id UUID NOT NULL REFERENCES build_job_audit(job_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMPTZ NOT NULL,

    PRIMARY KEY (tenant_id, idempotency_key)
);

The transaction should be:
BEGIN
  INSERT idempotency key
  INSERT build job
  INSERT queue/outbox event
COMMIT

If the key already exists:
same request hash -> return existing job
different request hash -> 409 Conflict

Apply to
Section 3.1 and Section 3.5.1
Define idempotency as a transactional API concern rather than merely an HTTP-header convention.

4. Section 3.5.1 — Durable Queue Is Not Defined Enough
Gap
The specification says:
Durable Queue guaranteeing at-least-once execution, visibility timeouts, and DLQ routing.
But no queue technology or queue contract is defined.
Risk
At-least-once delivery means duplicate execution is expected.
Therefore queue semantics must be explicitly reconciled with job-state semantics.

Solution
Define the queue contract independently of implementation technology.
Required properties:

Message ID
Job ID
Tenant ID
Attempt number
Enqueued timestamp
Visibility deadline
Lease owner
Trace/correlation ID

Worker acquisition should be:
queue delivery
      ↓
database lease acquisition
      ↓
state transition QUEUED → INGESTING
      ↓
processing

The database job state remains authoritative; the queue is only the delivery mechanism.
This is important because the queue itself should never become the system of record for build state.

Apply to
Section 3.5.1
Add:

The durable queue is a delivery substrate, not an authoritative job-state store.
5. Section 3.5.2 — Job State Machine Needs Formal Transition Rules
Gap
The state sequence is defined:
SUBMITTED
→ QUEUED
→ INGESTING
→ GOVERNANCE_VALIDATING
...

but permitted transitions, illegal transitions, and ownership rules are not defined.
Solution
Create a transition matrix.
Current	Allowed Next State
SUBMITTED	QUEUED, REJECTED
QUEUED	INGESTING, EXPIRED, CANCELLED
INGESTING	GOVERNANCE_VALIDATING, FAILED, CANCELLED
GOVERNANCE_VALIDATING	MERGING, FAILED, REJECTED
MERGING	COMPILING, FAILED
COMPILING	VERIFYING, FAILED, CANCELLED
VERIFYING	HASHING, FAILED
HASHING	PUBLISHING, FAILED
PUBLISHING	PERSISTING, RECONCILING, FAILED
PERSISTING	COMPLETED, RECONCILING
RECONCILING	PUBLISHED, FAILED
RETRY_WAIT	previous non-terminal state
any terminal state	no transition

Then enforce it in the database/service layer.
For example:

UPDATE build_job_audit
SET status = :new_status,
    version_id = version_id + 1
WHERE job_id = :job_id
  AND status = :expected_current_status
  AND version_id = :expected_version;

Require exactly one row affected.
Apply to
Section 3.5.2 and Section 4.1.1
The state machine should not exist only as documentation.

6. Section 3.5.2 — Worker Lease and Job State Are Two Different Locks
Gap
The architecture currently mixes:
queue visibility timeout,
worker lease,
database optimistic locking.
These are related but distinct mechanisms.
Solution
Define them separately:
Queue visibility timeout
    = message delivery protection

Worker lease
    = execution ownership

Optimistic version_id
    = state mutation concurrency protection

A worker must possess both:
valid worker lease
+
valid job-state version

to perform a state transition.
A stale worker must be rejected even if it continues executing after its lease expires.

Apply to
Section 3.5.2
Add a fencing token.

For example:

lease_generation = 42

Every state update includes:
WHERE lease_generation = 42

A replacement worker receives:
lease_generation = 43

The old worker can therefore no longer mutate state.
This is a major distributed-systems hardening measure.

Section 3.5 explicitly says:

      ↓

      ↓

      ↓
BCR idempotent registration
      ↓
DB reconciliation
      ↓
PUBLISHED

The BCR may still expose:

internally, but that should not be described as a distributed transaction.
It is an idempotent registration API invoked by the Saga.

Apply to
Sections 3.3.2, 3.3.3, 3.4.3, and 3.5.3
Replace language such as:

with:

where appropriate.
8. Section 3.5.3 — Saga Compensation Is Not Fully Defined
Gap
The Saga defines forward actions but not complete compensation semantics.
For example:

CAS published
BCR committed
PostgreSQL unavailable

What happens?
Solution
Explicitly define compensatable vs non-compensatable operations.
Operation	Compensation
Temporary CAS staging	Delete staging data
CAS final publication	No rollback; immutable
BCR artifact registration	Idempotent reconciliation
PostgreSQL manifest	Retry transaction
Build status	Reconcile

The important principle:
Published immutable artifacts are never deleted merely because downstream bookkeeping failed.
Instead:
PUBLISHING
   ↓
RECONCILING
   ↓
PUBLISHED

9. Section 3.3.3 / 4.2 — CAS Authority Needs a Distributed Storage Contract
Gap
The document simultaneously describes CAS as:
physical authoritative storage,
local filesystem,
potentially object storage,
and a secondary object-store failover.
The semantics of these stores are not defined.
Risk
Two CAS nodes could disagree about whether a blob exists.
Solution
Define CAS abstractly:
CAS Interface
 ├── put(digest, bytes)
 ├── get(digest)
 ├── exists(digest)
 ├── verify(digest)
 └── delete_staging(token)

Then define implementations:
LocalFilesystemCAS
ObjectStorageCAS

For production multi-node deployment, object storage should generally be the authoritative shared implementation, while local disk can be a cache/staging layer.
If local filesystem remains authoritative, the architecture needs explicit shared-volume/high-availability semantics.

Apply to
Section 4.2.3
Clarify:

CAS authority refers to the logical CAS service, not necessarily a specific physical storage implementation.

12. Section 4.1 — DAG Closure Complexity Is Still Incorrect
Gap
The architecture correctly recognized that graph retrieval is not inherently O(1), but the document still contains:
$O(1)$ lookup time using closure tables
A closure table can make reachability existence checks highly efficient, but retrieving an entire subgraph remains proportional to the result size.
Correct formulation
For a returned subgraph of V nodes and E edges:
O(V + E)

after indexed closure lookup.
For reachability existence:

O(log N)

or effectively constant-ish under particular indexed access patterns, but it should not be represented as a universal O(1) claim.
Apply to
Sections 4.1.2 and 5.1.1
Replace:

O(1) graph retrieval
with:
Indexed closure lookup followed by result-size-proportional graph materialization, O(V + E).

Overall Co-Architect Conclusion
The architecture has the right major building blocks, but it is now at the point where consistency between sections is more important than adding additional components.
The three architectural invariants I would make non-negotiable are:

1. One authoritative owner for every piece of state.
2. Every distributed operation must be idempotent and reconcilable rather than relying on distributed rollback.
3. Every artifact must be reproducible from a closed, cryptographically identified build-input manifest.
Once those three principles are enforced, the architecture becomes considerably easier to reason about:
BCR
  = specification authority

meta_builder + PostgreSQL
  = build-state authority

CAS
  = content authority

Queue
  = delivery mechanism

NetworkX
  = computation mechanism

Redis/cache
  = performance optimization

LLM
  = untrusted synthesis mechanism

Generator
  = orchestration/governance facade

That separation is the key architectural boundary I would carry forward into the next design stage.
The next logical section to formalize is Section 6: Control-Plane Data Contracts & State-Transition Protocols, because the remaining high-risk gaps are now concentrated around the exact database/outbox/queue/lease/event schemas and their atomic transition semantics.
