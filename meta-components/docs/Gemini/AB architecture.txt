# Application Builder Engine Architectural Specification

## 1. Executive Summary & Core Objectives

**1.1 System Purpose**
The Meta-Compiler Platform provides an extensible, asynchronous architectural engine designed for dynamic schema compilation, runtime model synthesis, and topology-validated graph execution. By decoupling infrastructure definitions from static deployment lifecycles, the system dynamically synthesizes Pydantic models via `meta_polymorph`, validates pipeline dependencies using NetworkX DAG structures within `meta_builder_brain`, and enforces state isolation across defined system boundaries. The system relies on the Blueprint Component Registry (`urn:meta:bcr:...`) as the authoritative registry for versioned specification manifests, state plane contracts, and spec deltas.

**1.2 Business Drivers**

* **Runtime Schema Elasticity**: Eliminates deployment overhead and redeployment cycles for minor data model updates by compiling dynamic Pydantic schemas on demand from spec deltas.
* **Decoupled Boundary Governance**: Offloads authorization decisions and dynamic credential management to sidecar Open Policy Agent (OPA) engines and OpenBao servers, isolating security controls from internal business logic.
* **Deterministic Execution Pipelines**: Prevents cyclic dependencies and execution deadlocks by validating pipeline graphs prior to launching AsyncIO task sequences.
* **Contract Standardization**: Unifies specification contracts across external, boundary, and internal planes using structured URN identifiers (`urn:meta:bcr:...`).
* **High-Throughput Asynchronous State Persistence**: Maintains low latency and persistent state auditability through pooled, non-blocking PostgreSQL connections managed via SQLAlchemy and AsyncPG.

## 2.1 Six-Plane Functional Scope & Authority Map

1. **Experience Plane**: Manages client interaction protocols across external interfaces. Ingests raw specifications via RESTful HTTP/gRPC endpoints or local CLI invocations.
2. **Control / Orchestration Plane**: Manages build execution lifecycles, durable job queueing, worker lease allocations, cancellation signals, and transactional publication outboxes.
3. **Governance Plane**: Enforces identity extraction, tenant boundary isolation, RBAC/ABAC Rego policies via Open Policy Agent (OPA), and dynamic secret injection via OpenBao.
4. **Registry Plane**: Authoritative source for all software blueprints, URN resolution (`urn:meta:bcr:...`), versioned component states (`DRAFT`, `ACTIVE`, `DEPRECATED`, `RETIRED`), and inheritance graph lineages.
5. **Compilation Plane**: Coordinates model synthesis (`meta_builder_brain`), polymorphic manifest merging (`meta_polymorph`), and 5-stage AST compilation (`meta_compiler`).
6. **Persistence Plane**: Enforces multi-tenant data storage split between immutable raw binary CAS blobs, append-only WORM log streams, and relational PostgreSQL database projections.

### 3.1 Specification Management Interface

**Functional Scope:**

The Specification Management Interface provides entry points (REST API and CLI) to ingest raw provider domain specifications, trigger validation runs, initiate component generation builds, poll execution progress, and retrieve output artifact manifests. It orchestrates execution flow into the Hybrid Governance & Validation Engine and coordinates spec retrieval and artifact registration with the Blueprint Component Registry (BCR).

The interface supports two distinct execution modes:

* **Direct Mode (`--mode direct`)**: Executes core python modules in-process for local development, offline builds, and CI runners. Bypasses network transport protocols but **strictly enforces** local identity context instantiation, OPA policy evaluation, tenant scoping, and spec lifecycle checks in-process.
* **Remote Mode (`--mode remote`)**: Acts as an HTTP/REST API client interacting with the centralized Application Builder Engine over TLS 1.3.

#### 3.1.1 Authentication & Workload Identity Contracts

All HTTP REST requests and Direct Mode invocations must supply explicit security credentials mapped to defined tenant boundaries.

* **Header Contracts:**
* `Authorization: Bearer <JWT>`: Standard OAuth2 / OIDC bearer token (RS256 signed) carrying `iss`, `sub`, and `tenant_id` claims.
* `X-Workload-Identity`: Optional short-lived token for CI/CD runners, exchanging platform identities (e.g., GitHub Actions OIDC, AWS IRSA) for ephemeral build permissions.
* `Idempotency-Key: <UUIDv4>`: Mandatory unique client key for mutation endpoints (`POST /v1/build/submit`).

#### 3.1.2 Transactional Idempotency Model

To guarantee at-most-once job creation during network retries or gateway failures, submission requests are governed by a transactional database idempotency table.

```sql
CREATE TABLE build_idempotency_keys (
    tenant_id UUID NOT NULL,
    idempotency_key VARCHAR(255) NOT NULL,
    request_sha256 CHAR(64) NOT NULL,
    job_id UUID NOT NULL REFERENCES build_job_audit(job_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (tenant_id, idempotency_key)
);

```

**Submission Atomic Execution Sequence:**

```
BEGIN TRANSACTION;
  1. INSERT INTO build_idempotency_keys (tenant_id, idempotency_key, request_sha256, job_id, expires_at);
     -- On Unique Violation (tenant_id, idempotency_key):
     --   IF request_sha256 matches existing -> RETURN existing job_id (200/202)
     --   IF request_sha256 differs -> ABORT & RETURN 409 Conflict
  2. INSERT INTO build_job_audit (job_id, tenant_id, status, ...);
  3. INSERT INTO build_queue_outbox (job_id, payload, ...);
COMMIT;

```

### 3.2 Hybrid Governance & Validation Engine

The **Hybrid Governance & Validation Engine** acts as the enforcement gatekeeper for the Meta-Compiler Platform. It verifies incoming provider domain specifications, untrusted LLM-synthesized intermediate representations (IRs), and delta extensions against immutability rules, topological constraints, and security policies before AST compilation.

#### 3.2.1 Granular Immutability & Permission Matrix

Immutability rules govern how extending or inheriting specifications (e.g., Provider tier) interact with parent attributes (e.g., Global or Industry blueprints). To prevent illegal structural modifications on containers, objects, and traits, field governance enforces discrete operation-level permission controls.

* **Immutability Permission Tiers:**
* **`FINAL`**: System invariant. Immutable field or structural node. Inheritance is strictly read-only.


* **`EXTENDABLE`**: Structural container (array, map, or trait set). Extending specs may append new items or keys, but cannot mutate, overwrite, or delete existing inherited items.


* **`OVERRIDABLE`**: Fully mutable node. Extending specs may alter values, default configurations, validation regexes, display metadata, or explicitly mark fields as disabled.





| Base Immutability Tier | `READ / INHERIT` | `ADD / APPEND` | `REPLACE / MUTATE` | `DELETE` | `DISABLE` | Enforcement Result on Breach |
| --- | --- | --- | --- | --- | --- | --- |
| **`FINAL`** | **ALLOWED** | REJECT | REJECT | REJECT | REJECT | Hard Governance Fault (`422` / `MBR-004`) |
| **`EXTENDABLE`** | **ALLOWED** | **ALLOWED** | REJECT | REJECT | REJECT | Structural Breach Fault (`422` / `MBR-005`) |
| **`OVERRIDABLE`** | **ALLOWED** | **ALLOWED** | **ALLOWED** | **ALLOWED** | **ALLOWED** | Validation Pass |

#### 3.2.2 Decoupled Three-Phase Validation Pipeline

Validation is decoupled into three sequential, isolated phases. This separation enables low-latency offline execution in Direct Mode, isolates failure domains, and prevents unnecessary network calls to external components when basic syntax or type checks fail.

##### Phase A: Pure Static & Structural Validation (In-Process / Offline)

* **Syntax & DET Schema Verification**: Validates payload structure against canonical Domain Entity Template (DET) definitions in-memory.
* **Untrusted LLM Synthesis Gating**: Inputs originating from LLM-driven synthesis (`meta_builder_brain`) are treated as unvalidated input. They undergo structural normalization, type lowering, and schema sanitization before proceeding.
* **Pre-Allocation Admission Controls**: Evaluates spec complexity prior to worker resource allocation. Rejects builds exceeding tenant admission bounds (e.g., `max_ast_nodes > 10000` or `max_payload_bytes > 10MB`) upfront to protect worker clusters from memory exhaustion.


* **Immutability Rule Evaluation**: Evaluates extending deltas against parent field constraints using the Granular Immutability Matrix.



##### Phase B: Resolution & Dependency Topology Validation (Registry Scope)

* **URN Resolution & Existence**: Resolves all referenced parent and component URNs against the Blueprint Component Registry (BCR) system of record.
* **Lifecycle State Enforcement**: Enforces transitive state rules across dependent specifications:
* `ACTIVE` dependencies $\rightarrow$ Pass.
* `DEPRECATED` dependencies $\rightarrow$ Pass with system audit warning (or halt if `--disallow-deprecated` is set).
* `RETIRED` or `DRAFT` dependencies $\rightarrow$ Reject with lifecycle fault (`MBR-007`).


* **Topological Cycle Detection**: Constructs a NetworkX DAG of component relationships to verify that the graph is strictly acyclic ($O(V + E)$ complexity). Enforces graph boundary bounds (`max_depth: 32`, `max_nodes: 10000`).

##### Phase C: Policy & Authorization Governance Validation (Governance Scope)

* **Decoupled OPA Evaluation**: Evaluates authorization contexts and security claims against OPA Rego policies.
* **Tenant Isolation**: Enforces multi-tenant segregation, ensuring tenants cannot reference or extend private URNs outside their allocated namespace scope (`urn:meta:bcr:provider:{tenant_id}:*`).
* **Direct Mode Parity Guarantee**: Direct Mode CLI execution runs identical Phase A, B, and C policies in-process using local policy bundles, ensuring security parity regardless of transport protocol.

#### 3.3.2 URN Resolution, Version-Level Lifecycle States & Resolution Policies

BCR uses Uniform Resource Names (URNs) as globally unique identifiers across all specification tiers and generated outputs.

* **URN Structure Protocol**:
`urn:meta:bcr:{scope}:{owner}:{category}:{name}:v{version}`

* *Blueprint Example*: `urn:meta:bcr:telecom:blueprints:Subscriber:v1.0.0`

* *Generated Code Example*: `urn:meta:bcr:provider:comcast:artifacts:SubscriberPydanticModel:v1.0.0`



* **Version-Specific Lifecycle State Machine**:
Lifecycle states apply strictly to an **immutable versioned record**, never to a floating logical component name. Retiring `Subscriber:v1.0.0` has zero impact on `Subscriber:v1.1.0`.



```
       +---------+          Validate & Publish          +----------+
       |  DRAFT  | -----------------------------------> |  ACTIVE  |
       +---------+                                      +----------+
            |                                                |
            | Abandon                                        | Deprecate
            v                                                v
       +---------+                                      +------------+
       | DELETED |                                      | DEPRECATED |
       +---------+                                      +------------+
                                                             |
                                                             | Retire
                                                             v
                                                        +---------+
                                                        | RETIRED |
                                                        +---------+

```

* `DRAFT`: Unverified, mutable specification under authoring; accessible only to validation dry-runs (`/v1/build/validate`).


* `ACTIVE`: Fully validated, immutable, production-ready record available for compilation. Content payload can never be mutated once published.


* `DEPRECATED`: Operational but marked for decommissioning; generates boundary compilation warnings.


* `RETIRED`: Read-only historical record; strictly rejected by `meta_builder` during new application synthesis.


* **Transitive Dependency Resolution Policies**:
During graph traversal, `meta_builder` evaluates root and transitive dependency states according to strict policy rules:



| Root Component State | Transitive Dependency State | Resolution Result | Execution Outcome |
| --- | --- | --- | --- |
| `ACTIVE` | `ACTIVE` | **PASS** | Normal compilation pass.

 |
| `ACTIVE` | `DEPRECATED` | **WARN / CONFIGURABLE** | Passes with audit alert unless `--disallow-deprecated` flag is set.

 |
| `ACTIVE` | `RETIRED` | **REJECT** | Compiler halt (`422 Unprocessable Entity` / `MBR-007`).

 |
| `DEPRECATED` | `ACTIVE` / `DEPRECATED` | **REJECT (Default)** | Permitted only if `allow_deprecated=true` in build payload.

 |
| Any State | `DRAFT` | **REJECT** | Drafts cannot serve as dependencies for active builds.

 |

* **Cache Trust Tiers & Edge Case Mitigations**:

| Edge Case Scenario | Failure Risk | Mitigation Mechanism | Cache / Partition Trust Protocol |

| **Deep Tree Latency** | Sequential HTTP fetches ($N+1$ queries).

 |
| **Network Partition** | Local cache out of sync during outage.

#### 3.3.3 Content-Addressed Storage (CAS), Bulk APIs & Saga Integration

To guarantee reproducibility and immutability across builds, BCR combines URN resolution with SHA-256 Content-Addressed Storage (CAS).

* **Bulk URN Graph Resolution Flow**:
To prevent HTTP sequential latency bottlenecks, `meta_builder` requests complete dependency graphs in a single operation.



```

```

1. **Bulk Resolution Call**: Engine sends `POST /v1/registry/artifacts/resolve-batch` containing entrypoint URNs.


2. **Graph Assembly**: BCR returns the full AST dependency graph along with resolved CAS SHA-256 addresses in a single payload.


3. **In-Memory Integrity Check**: `meta_builder` fetches CAS blobs and verifies that $\text{SHA256}(\text{blob\_bytes}) == \text{expected\_cas\_sha256}$ before passing payloads to `meta_compiler`.



* **Bulk Resolution Request Payload (`POST /v1/registry/artifacts/resolve-batch`)**:

```
 [ INGESTING ] ──> [ GOVERNANCE_VALIDATING ] ──> [ MERGING ] ──> [ COMPILING ]

| **`MERGING`** | `PolymorphAdapter` | Verified OPA compliance; parent blueprint URNs resolved.

| **`COMPILING`** | `CompilerAdapter` | Closed `ManifestIR` and `BuildInputDigest` produced.

| **`VERIFYING`** | `VerificationAdapter` | Raw unformatted code strings generated in-memory.

| **`PUBLISHING`** | `CASAdapter` / `BCRAdapter` | Formatted code strings and valid CAS digests verified.

 | **Saga Retry:** Trigger asynchronous outbox reconciliation.

 |
| **`PERSISTING`** | `PersistenceAdapter` | Artifacts committed to BCR and CAS.

 | PostgreSQL job status set to `COMPLETED`; DAG closure edges stored.

 | **Reconcile:** Outbox worker retries DB transaction until published.

### 3.5.1 Request Idempotency & Durable Delivery Contract

#### 1. Transactional Idempotency Ledger

To prevent duplicate execution jobs during network retries, gateway client disconnects, or upstream timeouts, the API boundary enforces strict transactional idempotency using an authoritative relational ledger (`build_idempotency_keys`) bound directly to the transactional outbox.

```sql
CREATE TABLE build_idempotency_keys (
    tenant_id UUID NOT NULL,
    idempotency_key VARCHAR(255) NOT NULL,
    request_sha256 CHAR(64) NOT NULL,
    job_id UUID NOT NULL REFERENCES build_job_audit(job_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (tenant_id, idempotency_key)
);
CREATE INDEX idx_idempotency_expires ON build_idempotency_keys(expires_at);

```

**Atomic Ingestion Execution Sequence:**
When a build submission (`POST /v1/build/submit`) arrives with an `Idempotency-Key` header, the database executes an atomic single-transaction sequence:

```
BEGIN TRANSACTION;
  1. INSERT INTO build_idempotency_keys (tenant_id, idempotency_key, request_sha256, job_id, expires_at)
     VALUES (:tenant_id, :idempotency_key, :request_sha256, :job_id, NOW() + INTERVAL '24 hours')
     ON CONFLICT (tenant_id, idempotency_key) DO NOTHING;

  2. IF NOT INSERTED (Conflict Detected):
        SELECT request_sha256, job_id FROM build_idempotency_keys
        WHERE tenant_id = :tenant_id AND idempotency_key = :idempotency_key;

        IF existing.request_sha256 == incoming.request_sha256 THEN
           ABORT TRANSACTION;
           RETURN Existing job_id (HTTP 200 OK / 202 Accepted); -- Idempotent Replay
        ELSE
           ABORT TRANSACTION;
           RETURN HTTP 409 Conflict (Payload mismatch for active idempotency key);
        END IF;

  3. INSERT INTO build_job_audit (job_id, tenant_id, status, current_stage, ...);
  4. INSERT INTO build_queue_outbox (job_id, tenant_id, payload, enqueued_at);
COMMIT;

```

* **Transactional Outbox Worker**: An outbox process polls `build_queue_outbox` within the database transaction boundary, pushing dispatch messages to the durable queue (e.g., RabbitMQ, AWS SQS) and purging outbox entries upon publisher confirmation.


* **Message Envelope & Trace Context**: Queue envelopes carry mandatory telemetry context (`trace_id`, `span_id`) for distributed tracing (Item #41) alongside execution parameters:

### 3.5.2 State Machine, Dual-Lock Fencing & Transition Matrix

#### 1. Canonical 14-State Engine & Orthogonal Sub-Flags

To eliminate state fragmentation (Item #48), execution progresses strictly through a unified 14-state machine. Pipeline operations are distinct from status conditions: status tracks macro-lifecycle, while orthogonal sub-state flags track non-blocking operational conditions.

* **Canonical States**: `SUBMITTED` $\rightarrow$ `QUEUED` $\rightarrow$ `INGESTING` $\rightarrow$ `GOVERNANCE_VALIDATING` $\rightarrow$ `MERGING` $\rightarrow$ `COMPILING` $\rightarrow$ `VERIFYING` $\rightarrow$ `HASHING` $\rightarrow$ `PUBLISHING` $\rightarrow$ `PERSISTING` $\rightarrow$ `COMPLETED`.


* **Terminal Fault States**: `FAILED`, `REJECTED`, `CANCELLED`.


* **Orthogonal Sub-State Flags**: `cancel_requested` (boolean), `retry_wait` (boolean), `reconciling` (boolean).



#### 2. Dual-Lock Fencing Protocol (`lease_generation` + `version_id`)

To prevent "zombie workers" (workers delayed by GC pauses, network partitions, or cgroup throttling) from corrupting active builds, every state mutation requires a dual-lock fencing query:

1. **Worker Monotonic Lease (`lease_generation`)**: Incremented sequentially every time a worker claims or extends a job lease.


2. **Optimistic Entity Version (`version_id`)**: Incremented on every row update to prevent concurrent mutation races.



```sql
UPDATE build_job_audit
SET status = :new_status,
    current_stage = :new_stage,
    progress_percentage = :new_progress,
    version_id = version_id + 1,
    lease_expires_at = CURRENT_TIMESTAMP + INTERVAL '300 seconds'
WHERE job_id = :job_id
  AND tenant_id = :tenant_id
  AND status = :expected_current_status
  AND version_id = :expected_version_id
  AND lease_generation = :assigned_lease_generation
  AND (lease_expires_at > CURRENT_TIMESTAMP OR status = 'QUEUED');

```

* **Fence Breach Protocol**: If `ROWCOUNT == 0`, the worker has lost its fence lease. The worker process must immediately abort execution, discard local in-memory ASTs, release local disk staging buffers (`/cas/staging/*`), and refrain from issuing downstream BCR or DB writes.



#### 3. Formal State Transition Matrix

| Current State | Permitted Next States | Trigger / Operational Condition | Mutation & Governance Guard |
| --- | --- | --- | --- |
| **`SUBMITTED`** | `QUEUED`, `REJECTED` | API payload ingestion & outbox enqueue. | Outbox DB Transaction |
| **`QUEUED`** | `INGESTING`, `CANCELLED` | Worker claims message; acquires initial lease (`lease_generation + 1`). | Fencing Lock (`lease_generation`) |
| **`INGESTING`** | `GOVERNANCE_VALIDATING`, `FAILED`, `CANCELLED` | Input spec parsed into normalized `UNTRUSTED IR`. | Dual-Lock (`lease_generation`, `version_id`) |
| **`GOVERNANCE_VALIDATING`** | `MERGING`, `FAILED`, `REJECTED`, `CANCELLED` | OPA policy & tenant isolation check complete. | Phase A/B/C Gate Pass |
| **`MERGING`** | `COMPILING`, `FAILED`, `CANCELLED` | Delta manifests merged into canonical `ManifestIR`. | Immutability Matrix Pass |
| **`COMPILING`** | `VERIFYING`, `FAILED`, `CANCELLED` | Code generation & NetworkX DAG cycle check succeed. | Acyclic DAG Verification ($O(V+E)$) |
| **`VERIFYING`** | `HASHING`, `FAILED`, `CANCELLED` | Linter (`ruff`), typing (`mypy`), & Temporal checks pass. | VerificationProfile Compliance |

| **`COMPLETED`** *(Terminal)* | *None* | Execution successful. Immutable state. | DB Read-Only Enforcement |
| **`FAILED`** *(Terminal)* | *None* | Fatal execution or verification error encountered. | DB Read-Only Enforcement |

| **`CANCELLED`** *(Terminal)* | *None* | Cooperative cancellation finalized by worker. | DB Read-Only Enforcement |

### 3.5.3 Idempotent Artifact Publication Saga & Non-Rollback Semantics

To prevent partial publication hazards where multi-artifact builds leave orphaned files or inconsistent schemas (Item #47), publication executes as an **Idempotent Publication Saga** using the **Build Artifact Manifest** as the single atomic unit of publication.

```
           WORKER / COMPILER                 CAS STORAGE SERVICE               BCR REGISTRY ENGINE
                  │                                  │                                  │
  1. Write Local Staging Files ────────────────────> │ Staging Buffer                   │
     (/cas/staging/{job_id}/*.tmp)                   │ (/cas/staging/...)               │
                  │                                  │                                  │
  2. Compute SHA-256 & Generate Manifest             │                                  │
                  │                                  │                                  │
  3. Reserve BCR Artifact URNs ────────────────────────────────────────────────────────> │ POST /v1/registry/artifacts/reserve
                  │                                                                     │ (Returns Reservation Token)
  4. Promote CAS Blobs ────────────────────────────> │ Promote to Final Path            │
                  │                                  │ (/cas/sha256/xx/yy/digest.bin)    │
  5. Commit BCR Artifact Bundle ──────────────────────────────────────────────────────> │ POST /v1/registry/artifacts/commit
                  │                                                                     │ (Idempotent CAS-to-URN Bind)
  6. Finalize DB Transaction ──┐                     │                                  │
     (Set COMPLETED in DB)     │                     │                                  │
                               v                     │                                  │

```

#### Non-Rollback Governance & Forward Reconciliation

Because published CAS binaries and active BCR URN mappings are **strictly immutable**, failures during steps 4, 5, or 6 **do not roll back** or delete already-published CAS blobs or registered BCR entries. Rolling back immutable assets destroys audit lineage. Instead, the system applies forward compensation and asynchronous outbox reconciliation:

| Failure Point | Operational Impact | Compensation & Reconciliation Strategy |
| --- | --- | --- |
| **Failure during CAS Promotion (Step 4)** | Staging files exist; CAS promotion incomplete. | Worker deletes local temporary files in `/cas/staging/`. Job transitions to `FAILED` with RFC-7807 detail.

 |
| **Failure during BCR Commit (Step 5)** | Blobs promoted to CAS; BCR registry unbound. | Background Outbox Recovery Worker polls uncommitted reservations, re-issues `POST /v1/registry/artifacts/commit` using `BuildInputDigest`. Call is idempotent; duplicate writes yield `200 OK`.

 |
| **Failure during DB Finalization (Step 6)** | CAS promoted & BCR committed; DB status stale. | Recovery Worker checks BCR for active URN matching `job_id`. Upon verification, updates `build_job_audit` to `COMPLETED` (Forward Reconciliation).

 |

### 3.5.4 Cooperative Cancellation, Timeout Taxonomy & Retry Matrix

#### 1. Cooperative Cancellation Contract

Hard process termination (`SIGKILL`) during build compilation runs the risk of leaving orphaned staging buffers or corrupted local caches. The platform enforces cooperative cancellation:

1. **Cancellation Trigger**: A client invokes `POST /v1/build/status/{job_id}/cancel`.
2. **Flag Mutation**: The API Gateway sets `sub_state_flags.cancel_requested = true` in `build_job_audit`.
3. **Worker Checkpoint Evaluation**: The worker thread checks the `cancel_requested` flag at stage entry/exit gates (`INGESTING`, `MERGING`, `COMPILING`, `VERIFYING`).
4. **Safe Offboarding**: If `cancel_requested == true`, the worker halts AST compilation, cleans up `/cas/staging/{job_id}/` temporary disk buffers, emits a `BUILD_CANCELLED` audit event, and updates status to `CANCELLED`.
5. **Point-of-No-Return Boundary**: Once a build enters `PUBLISHING`, cancellation requests are deferred until publication finishes to preserve registry atomicity.

#### 2. Comprehensive Timeout Taxonomy (Item #39)

| Timeout Metric | Target Scope | Default Limit | Action on Expiry |
| --- | --- | --- | --- |
| **API Request Gateway Timeout** | Inbound REST/gRPC connection | $10\text{ seconds}$ | Abort HTTP request; return `504 Gateway Timeout`. |
| **Queue Message Visibility Timeout** | Message ack deadline in queue | $300\text{ seconds}$ | Queue re-surfaces message for alternate worker pick-up. |
| **Worker Lease Duration (`lease_expires_at`)** | Active database execution lease | $300\text{ seconds}$ | Lease expires; background recovery worker reclaims job. |

#### 3. Error Classification & Full-Jitter Retry Strategy (Item #40)

Exceptions encountered during orchestration are categorized into deterministic (non-retryable) faults and transient (retryable) infrastructure faults:

```python
import random
import logging

logger = logging.getLogger("meta_builder.orchestrator")

# Error Classification Taxonomy
DETERMINISTIC_ERRORS = (
    SyntaxError,
    TypeError,
    ValueError,
    ImmutabilityViolationError,  # MBR-004
    DAGTopologicalCycleError,   # MBR-005
    GovernancePolicyDeniedError # MBR-003 / 403
)

TRANSIENT_ERRORS = (
    DatabaseConnectionTimeout,
    BCRRegistryUnavailableError, # 503
    CASStorageIOException,
    OPASidecarTimeoutException  # 503
)

def calculate_full_jitter_backoff(attempt: int, base_sec: float = 1.0, max_sec: float = 60.0) -> float:
    """Calculates exponential backoff with full jitter to prevent thundering herds."""
    temp = min(max_sec, base_sec * (2 ** attempt))
    return random.uniform(0, temp)

def handle_execution_exception(job_id: str, attempt: int, max_attempts: int, exc: Exception):
    if isinstance(exc, DETERMINISTIC_ERRORS):
        logger.error(f"Deterministic fault encountered for job {job_id}: {exc}. Terminating build immediately.")
        transition_job_status(job_id, new_status="FAILED", retry=False)
    elif isinstance(exc, TRANSIENT_ERRORS) and attempt < max_attempts:
        backoff_delay = calculate_full_jitter_backoff(attempt)
        logger.warning(f"Transient fault for job {job_id} (Attempt {attempt}/{max_attempts}): {exc}. Retrying in {backoff_delay:.2f}s.")
        schedule_re_enqueue(job_id, delay_sec=backoff_delay)
    else:
        logger.critical(f"Exhausted retries or unhandled exception for job {job_id}: {exc}.")
        transition_job_status(job_id, new_status="FAILED", retry=False)

```

**Zero-Downtime Migration Protocol (Item #45):**
Database schema evolutions strictly adhere to an **Expand $\rightarrow$ Migrate $\rightarrow$ Contract** deployment pattern:

1. **Expand**: Add non-null defaultable columns, new tables, or new indexes without dropping or mutating active fields.
2. **Migrate**: Deploy dual-writing application instances capable of writing to both legacy and expanded structures while reading back-compatible formats.
3. **Contract**: Remove legacy columns and triggers only after all application workers have updated and verified the expanded schema state.

##### 4.1.2 Cryptographic Event Chaining & External WORM Anchoring (Item #25)

To guarantee immutable execution logs, `build_job_events` maintains a cryptographic hash chain. Each event entry computes its hash $H_n$ over its sequence index, payload, and the preceding event hash $H_{n-1}$:

$$H_n = \text{SHA256}(H_{n-1} \parallel \text{SequenceNo} \parallel \text{EventType} \parallel \text{CanonicalJSON}(\text{EventPayload}))$$

* **WORM Anchor Checkpoints**: To prevent database superuser tampering or retroactive log alteration, background persistence workers periodically generate signed checkpoint manifests ($H_N$). These checkpoints are written to an external Write-Once-Read-Many (WORM) storage bucket (e.g., AWS S3 Object Lock in Compliance Mode) and anchored with a KMS digital signature.

##### 4.1.3 Closure Table Lineage Retrieval Complexity (Item #35)

To eliminate performance degradation caused by recursive common table expression (CTE) graph queries during runtime compilation, ancestor/descendant lineage trees are maintained within `dag_lineage_closure`.

* **Retrieval Complexity**: Fetching complete inherited blueprint subgraphs or component dependency trees executes as a single indexed lookup:

$$\text{Time Complexity} = O(V + E)$$

Where $V$ represents the number of ancestor nodes and $E$ represents the edge count within the closure subgraph, eliminating iterative round-trips to the database engine.

##### 4.2.2 Transactional URN Registration & Collision Semantics (Item #34)

When registering generated artifacts against `artifact_manifests`, the engine executes an atomic registration transaction:

```
BEGIN TRANSACTION;
  1. INSERT INTO artifact_manifests (artifact_urn, tenant_id, cas_sha256, build_input_sha256, ...)
     VALUES (:urn, :tenant_id, :cas_sha256, :build_input_sha256, ...)
     ON CONFLICT (artifact_urn) DO NOTHING;

  2. IF NOT INSERTED (Conflict Detected):
        SELECT cas_sha256 FROM artifact_manifests WHERE artifact_urn = :urn;

        IF existing.cas_sha256 == incoming.cas_sha256 THEN
           ABORT TRANSACTION;
           RETURN HTTP 200 OK; -- Idempotent success (identical artifact content digest)
        ELSE
           ABORT TRANSACTION;
           RETURN HTTP 409 Conflict; -- Content collision for identical URN version
        END IF;
COMMIT;

##### 4.2.3 CAS Physical Layout & Staging Protocols

* **Storage Path Scheme**: `/cas/sha256/{digest[0:2]}/{digest[2:4]}/{full_digest}.bin`
* **Write Atomicity**: Blobs are written to a staging directory (`/cas/staging/{job_id}/{token}.tmp`). Upon validation, the physical CAS service invokes `put(digest, bytes)`, performing atomic link/rename operations into the physical storage tree.


* **Cleanup Strategy**: If a build cancels or encounters a validation failure prior to the `PUBLISHING` stage, `delete_staging(token)` purges all temporary files from `/cas/staging/` to prevent orphaned disk allocations.

#### 5.2 Security, Multi-Tenant Governance & Audit Integrity

##### 5.2.1 Authentication & Authoritative RBAC/ABAC

* **Authentication Protocol & Key Rotation**: Inbound API requests and CLI invocations supply OAuth2/OIDC JWT Bearer tokens signed via RS256. Tokens must contain valid claims (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `tenant_id`). Signature keys are dynamically retrieved and validated using an automated JWKS (JSON Web Key Set) discovery loop with cached TTLs and graceful key rotation fallback.


* **Decoupled Policy Engine**: Open Policy Agent (OPA) sidecars evaluate RBAC/ABAC Rego rules before job dispatch. Policy rules enforce strict namespace isolation (`urn:meta:bcr:provider:{tenant_id}:*`) to block unauthorized cross-tenant specification access.



##### 5.2.2 Multi-Tenant Isolation & Untrusted LLM Boundaries

* **Database Row-Level Security (RLS)**: PostgreSQL tables (`build_job_audit`, `build_job_events`, `artifact_manifests`, `build_idempotency_keys`) enforce mandatory `tenant_id` columns paired with RLS policies (`USING (tenant_id = current_setting('app.tenant_id')::uuid)`).


* **Untrusted LLM IR Boundary**: Synthesized specs from `meta_builder_brain` are ingested as `UNTRUSTED IR`. LLM outputs cannot directly drive code generation; they must pass schema validation, OPA governance, and canonical normalization into an immutable `ManifestIR`.


* **Configurable Verification Profiles**: Verification strictness and typing modes are specified via `VerificationProfile` configurations embedded within the `BuildReproducibilityManifest`, establishing target-specific quality gates without breaking compilation reproducibility.



##### 5.2.3 Cryptographic Audit Streams & Secrets Management

* **Append-Only Event Chaining & WORM Anchoring**: Audit events are written to an append-only `build_job_events` store. Events are cryptographically chained using SHA-256 ($H_n = \text{SHA256}(H_{n-1} \parallel \text{EventPayload}_n)$) to prevent retroactive tampering. Event chain heads ($H_N$) are anchored periodically via signed checkpoint manifests written to external WORM storage (e.g., AWS S3 Object Lock).


* **Dynamic OpenBao Secrets Leasing**: Storage keys, KMS signing handles, and database credentials are dynamically leased from OpenBao using short-lived AppRole tokens. Background renewal loops manage token leases; if renewal fails or a token is revoked, workers initiate non-blocking execution drain and halt new processing loops. All log streams and RFC-7807 payloads pass through automated string filters to scrub sensitive credentials prior to persistence.

#### 5.3 Operational Failure Modes & Mitigation Matrix

The system operates under a fail-closed, zero-silent-failure design policy across all planes.

| Failure Scenario | System Detection Mechanism | Automated Mitigation & Recovery Strategy | Operational State |
| --- | --- | --- | --- |
| **DB Connection Pool Exhaustion** | Pool checkout time exceeds $30\text{ s}$, raising `TimeoutError`.

 | Circuit Breaker Active

 |
| **Recursive AST Lineage Cycle** | NetworkX `simple_cycles()` detects directed graph cycle.

 | Aborts merge pipeline prior to stack overflow; returns RFC-7807 error payload detailing circular path (max depth $N_{\text{max}} = 32$).

 | Validation Rejection (`422`)

 |
| **CAS Blob Storage Corruption** | SHA-256 mismatch on read OR physical volume capacity $> 90\%$.

 | Storage Failover (`500`)

 |
| **OPA Sidecar Timeout / Crash** | Connection timeout ($> 200\text{ ms}$) on local sidecar socket.

 | Enforces fail-closed governance; rejects mutation operations with `503 Service Unavailable`; read ops fallback to locally signed policy bundles.

 | Governance Lockdown (`503`)

 |
| **Stale Worker / GC Pause Breach** | Dual-lock database fencing check fails (`lease_generation` mismatch).

| **Worker RAM Exhaustion** | Process RAM exceeds cgroup threshold during `mypy` pass.

### State Mutation Guard Statement

For any transition from $S_{\text{current}}$ to $S_{\text{next}}$, workers execute the following single atomic update:

```sql
UPDATE build_job_audit
SET status = :next_status,
    current_stage = :next_stage,
    progress_percentage = :progress,
    version_id = version_id + 1,
    lease_expires_at = CURRENT_TIMESTAMP + INTERVAL '300 seconds'
WHERE job_id = :job_id
  AND tenant_id = :tenant_id
  AND status = :current_status
  AND version_id = :expected_version_id
  AND lease_generation = :assigned_lease_generation
  AND (lease_expires_at > CURRENT_TIMESTAMP OR status = 'QUEUED');

```

## 6.4 Publication Saga & Forward Reconciliation Protocol

When a build reaches the target artifact publication step, distributed atomic guarantees are achieved using an **Idempotent Artifact Publication Saga** rather than distributed locking.

1. **Step 1 (Staging Writes)**: Formatted code binaries are staged to localized worker paths (`/cas/staging/{job_id}/*.tmp`).


2. **Step 2 (BCR URN Reservation)**: Worker issues `POST /v1/registry/artifacts/reserve` to BCR, receiving a temporary reservation token.


3. **Step 3 (CAS Blob Promotion)**: Blobs are promoted to physical storage path locations (`/cas/sha256/xx/yy/{hash}.bin`).


4. **Step 4 (BCR Idempotent Commit)**: Worker calls `POST /v1/registry/artifacts/commit`, linking the CAS SHA-256 digests to the reserved URNs.


5. **Step 5 (DB Finalization)**: Worker updates `build_job_audit` to `COMPLETED` and commits localized database projections.



### Forward Reconciliation Matrix

Immutable CAS blobs and committed BCR registry entries are never deleted or rolled back if downstream database steps fail. If step 5 encounters a database crash or connection loss, a background **Recovery Worker** performs non-rollback forward reconciliation:

| Point of Disruption | Observed System State | Recovery Worker Reconciliation Sequence |
| --- | --- | --- |
| **Post-Step 3 Fail** | Blobs in CAS; BCR uncommitted; DB in `PUBLISHING`. | Worker re-executes Step 4 (`POST /commit`). Call is idempotent; yields `200 OK` and proceeds to Step 5.

 |
| **Post-Step 4 Fail** | Blobs in CAS; BCR committed `ACTIVE`; DB in `PUBLISHING`. | Worker queries BCR for URN matching `job_id`. Confirms active status and updates DB directly to `COMPLETED`.

 |
| **Stale Worker Lock** | Worker dead; `lease_expires_at` passed. | Recovery worker increments `lease_generation = lease_generation + 1`, reclaims job context, and resumes execution from last verified stage checkpoint.

 |
