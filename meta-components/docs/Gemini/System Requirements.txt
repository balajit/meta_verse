**Requirements Specification: Application Builder Engine (`meta_builder`)**

This document establishes the architectural requirements, domain modeling specifications, and edge cases captured during the high-level design phase for the `meta_builder` framework.

---

### **1. Core System Philosophy & Architecture**

* **Layered Namespace Model (Zero-Redundancy Hierarchy):**
* **Global Namespace:** Enforces system-wide defaults, standard data types, global compliance rules (GDPR, PII handling), cryptographic requirements, and default primary key behaviors.
* **Industry Namespace:** Provides domain-specific patterns, regulatory retention rules, standard base models (e.g., `Telecom.Subscriber`), and shared entity abstractions.
* **Specific Provider Namespace (User Spec):** Contains the minimal delta input authored by the developer/business user. Inherits from Industry/Global layers and defines custom overrides.


* **Declarative Specification Over Boilerplate:** Users define *intent* via a minimal Domain Entity Template (DET). `meta_builder_brain` inflates this specification using global/industry context before compilation.

---

### **2. Domain Entity & Lifecycle Rules**

* **Entity Classification:**
* **Embedded Value Objects (Lifecycle Bound):** Structs/objects tied directly to the parent entity. Deleting or archiving the parent cascades to these objects (e.g., User Preferences).
* **Linked Independent Entities (Lifecycle Decoupled):** Autonomous entities that persist independently of the parent record. Deleting or updating the parent entity MUST NOT destroy or invalidate the independent entity (e.g., a `ServiceableLocation` remains active in a cable system even if a `User` cancels their service).


* **Compliance & Governance Automation:**
* Declarative field tags (e.g., `PII`, `AuditLog`) automatically trigger data encryption, sanitization, and state-transition event logging in the generated codebase.



---

### **3. Module Specification Requirements (User Management Example)**

#### **Entities & Relationships**

* **User (Core Entity):**
* Requires exactly 1 `Service Address` (Linked Independent Entity).
* Has 0 or more `Contact Methods` (Embedded Collection).


* **Address Model:**
* Must support independent lifecycle management (persists across user relocations or service disconnections).


* **Contact Model:**
* Contains `Type` and `Value`. Enforces uniqueness per contact type per user (e.g., maximum 1 primary email).



#### **Required Module Operations**

* **User Search:** Dynamic, multi-criteria lookup supporting exact and partial matching across `Name`, `Contact Info`, and `Address/Location`.
* **User Creation:** Validates and creates a User along with their required initial Address and optional Contact methods.
* **Address Change:** Atomically replaces or updates the associated Address reference without destroying historical location data.
* **Contact Management:** Performs differential updates (add, update, remove) on a user's contact collection while enforcing constraint uniqueness.

---

### **4. System Edge Cases & Design Considerations**

* **Lifecycle Decoupling & Orphan Management:**
* *Edge Case:* A User entity is purged (e.g., GDPR "Right to be Forgotten").
* *Requirement:* `meta_polymorph` must generate foreign key handling (`ON DELETE SET NULL` or soft-delete decoupling) so the linked `ServiceableLocation` is preserved for historical audit and statutory compliance, while PII fields are scrubbed.


* **Search Parameter Permutations:**
* *Edge Case:* Searching by a non-existent contact type or combining conflicting filters (e.g., searching by an address that belongs to a different tenant).
* *Requirement:* Generated repository methods must safely handle optional parameter combinations without resorting to dynamic string-concatenated SQL/queries.


* **Cascade Mutability vs. Immutability:**
* *Edge Case:* Multiple users (e.g., household members) share a single `ServiceableLocation`, and one user updates their address.
* *Requirement:* The system must differentiate between mutating an existing shared entity versus unlinking the user and linking them to a new/different independent entity record.



---

### **5. Component Responsibilities Matrix**

| Core Component | Responsibility |
| --- | --- |
| **`meta_builder_brain`** | Ingests minimal Provider DET, resolves namespace inheritance (Global $\rightarrow$ Industry $\rightarrow$ Provider), expands implicit traits, and builds the unified Domain Graph. |
| **`meta_polymorph`** | Generates dynamic data contracts, applies relationship cascade policies (Bound vs. Independent), and resolves multi-criteria lookup signatures. |
| **`meta_compiler`** | Compiles the expanded AST into executable Python code (models, services, repositories) and generates deterministic `unittest` and integration test suites. |

### **Next Step: The Industry Registry**

Treating the Industry Registry like a **library catalog** is an intuitive, highly effective pattern. In library systems, you have call numbers, canonical catalog entries, versioned editions, cross-references, and strict indexing.

Applying catalog mechanics to `meta_builder` gives us a clean model for finding, extending, and composing pre-packaged domain entities.

---

### **The Library Catalog Pattern for Industry Registries**

```
 📚 CATALOG INDEX (URN-based Lookup)
 ├── urn:meta:industry:telecom:v1
 │    ├── 📄 Subscriber (Base Entity)
 │    ├── 📄 ServiceableLocation (Independent Entity)
 │    └── 📄 ServicePlan (Catalog Value Object)
 └── urn:meta:industry:healthcare:v1
      └── 📄 Patient (Base Entity)

```

#### **1. Universal Resource Names (URNs) as Call Numbers**

Instead of arbitrary paths, every pre-packaged entity pattern receives a unique, versioned URN:

* `urn:meta:industry:telecom:entities:ServiceableLocation:v1`
* `urn:meta:industry:telecom:entities:Subscriber:v2`

**Why it works:** When a developer writes a minimal Provider spec, they simply reference the catalog URN. `meta_builder_brain` uses this URN to fetch the canonical spec from the local registry cache or a shared registry service.

---

#### **2. Card Catalog Metadata Structure**

Each catalog entry contains three clear sections: **Interface Contract**, **Default Lifecycle Behavior**, and **Extension Hooks**.

```yaml
# Catalog Entry: ServiceableLocation
catalog_urn: urn:meta:industry:telecom:entities:ServiceableLocation:v1
type: IndependentEntity
governance:
  retention_period: "7_years"
  default_orphan_policy: "PERSIST"

attributes:
  location_id: { type: UUID, primary_key: true }
  street_address_1: { type: String, required: true, pii: false }
  street_address_2: { type: String, required: false }
  city: { type: String, required: true, searchable: true }
  state: { type: String, required: true, searchable: true }
  postal_code: { type: String, required: true, searchable: true }
  country_code: { type: String, default: "US", iso_standard: "ISO-3166" }

extension_points:
  allow_custom_attributes: true
  allowed_overrides: ["postal_code_format", "country_code"]

```

---

#### **3. Key Advantages of the Catalog Approach**

* **Editioning & Versioning (Strict Backwards Compatibility):** Just as a library maintains multiple editions of a reference manual, the registry can host `v1` and `v2` of `ServiceableLocation`. Providers can upgrade on their own timeline without breaking downstream code generator pipelines.
* **Cross-Referencing & Composition:** Entities in the catalog can "cite" or compose other catalog entities. For example, `Subscriber:v1` can list a required relationship to `ServiceableLocation:v1` directly in its card catalog definition.
* **Discoverability & CLI Inspection:** A developer building a new module can query the CLI catalog just like searching an online public access catalog (OPAC):
```bash
meta_builder catalog search --industry telecom
meta_builder catalog inspect urn:meta:industry:telecom:entities:ServiceableLocation:v1

```



---

#### **4. Dynamic Resolution Flow**

When `meta_builder_brain` processes a minimal Provider spec:

1. **Catalog Lookup:** Resolves the requested URNs from the catalog index.
2. **Inheritance & Merge:** Injects the catalog entry's fields, compliance policies, and orphan behaviors into the target module.
3. **Delta Check:** Verifies that any local Provider overrides conform to the catalog entry's `extension_points` rules.

---
That balance—**guardrails, not handcuffs**—is critical for an enterprise-grade framework. If you lock down the schema too tightly, developers will bypass the system entirely; if you leave it completely open, regulatory compliance and schema predictability crumble.

Using URN indexing paired with a structured **Extension & Override Policy** gives us safety by default while offering an explicit, auditable escape hatch for intentional overrides.

---

### **1. The Mechanics: Guarded Extension Rules**

To prevent accidental breaches while allowing explicit customization, catalog attributes and constraints are categorized into three **Immutability Tiers**:

* **`FINAL` (Non-Overridable):** Enforces hard statutory or compliance bounds (e.g., GDPR wipe compliance, PII encryption flags, primary identifier structure). Overriding a `FINAL` property requires a formal compliance bypass declaration.
* **`EXTENDABLE` (Default):** Providers can add custom attributes or append local validation rules without breaking the core contract.
* **`OVERRIDABLE`:** Intentionally permissive defaults (e.g., regex patterns, default values, localized label strings) meant to be customized per provider.

---

### **2. Catalog Schema Definition (`ServiceableLocation:v1`)**

Here is how the Industry Catalog entry defines its parameters, bounds, and extension rules:

```yaml
catalog_urn: urn:meta:industry:telecom:entities:ServiceableLocation:v1
type: IndependentEntity

governance:
  retention_period: "7_years" # FINAL: Statutory record keeping
  default_orphan_policy: "PERSIST" # FINAL: Address survives subscriber deletion

attributes:
  location_id:
    type: UUID
    immutability: FINAL

  postal_code:
    type: String
    searchable: true
    immutability: OVERRIDABLE
    default_format: "^[0-9]{5}(-[0-9]{4})?$" # US ZIP default

  country_code:
    type: String
    immutability: OVERRIDABLE
    default: "US"

extension_policy:
  allow_additional_fields: true # Allows providers to attach local attributes
  require_override_justification: true # Force audit trail if OVERRIDABLE fields change

```

---

### **3. Provider Spec: Expressing Intentional Overrides**

When a provider needs to adjust an `OVERRIDABLE` field or add new attributes, they declare it explicitly. If they attempt to override a `FINAL` field, `meta_builder_brain` flags a compilation error unless an explicit `--force-compliance-bypass` key is supplied during build time.

```yaml
namespace: Provider.Comcast.UserManagement
extends: urn:meta:industry:telecom:entities:ServiceableLocation:v1

# 1. ADDING CUSTOM FIELDS (Allowed by extension_policy)
custom_attributes:
  drop_type: Choice(Aerial, Underground) | Required
  node_id: Text | Searchable

# 2. INTENTIONAL OVERRIDES (Audited and validated against Immutability Tiers)
overrides:
  - target: attributes.postal_code.default_format
    value: "^[A-Z][0-9][A-Z] [0-9][A-Z][0-9]$" # Canadian Postal Code format
    justification: "Expanding service area to Canadian market."

  - target: attributes.country_code.default
    value: "CA"
    justification: "Canadian regional deployment."

```

```
 └─────────────┬─────────────┘

 ┌───────────────────────────┐
```

The `type` field in the **Catalog Schema Definition** acts as the fundamental **structural and behavioral classification archetype** for an entity.

When `meta_builder_brain` parses an entity, `type` tells the engine how to construct database tables, handle primary keys, generate dynamic query strategies in `meta_polymorph`, and emit foreign key deletion constraints (e.g., cascade vs. preserve) in `meta_compiler`.

Here is a breakdown of the primary `type` values, what they indicate structurally to `meta_builder`, and concrete real-world domain examples for each.

---

### **1. `IndependentEntity**`

* **What it indicates:** An entity with its own independent primary key and autonomous lifecycle. It exists regardless of whether other entities link to it, and its records are preserved when related entities are deleted or deactivated.
* **Engine Behaviors Generated:**
* Independent database table/repository with its own ID generation strategy.
* Relationships targeting this entity use `ON DELETE SET NULL` or soft-delete decoupling.
* Top-level CRUD APIs and direct lookup endpoints generated by default.


* **Concrete Example:** `ServiceableLocation` (Telecom)
* *Why:* A residential house or utility pole exists independently of the customer paying for service. If the customer cancels their account or moves away, the physical address record remains intact in the system for the next tenant or for historical service logs.



---

### **2. `DependentEntity` (Owned Entity)**

* **What it indicates:** An entity that has its own identity and structure, but whose existence is completely bound to a parent entity. It cannot exist as an orphan in the system.
* **Engine Behaviors Generated:**
* Child database table linked via a non-nullable foreign key to the parent.
* Parent deletion automatically triggers `ON DELETE CASCADE` or recursive hard/soft wipes.
* Access is strictly scoped through the parent repository/service (no standalone creation endpoints without a parent ID).


* **Concrete Example:** `TroubleTicket` (Telecom / IT Ops)
* *Why:* A support ticket cannot exist floating in a vacuum; it must be tied to a specific `Subscriber` or `Account`. If the account record is completely scrubbed from the system (e.g., via GDPR compliance), all associated trouble tickets are purged with it.



---

### **3. `EmbeddedValueObject**`

* **What it indicates:** A structured, immutable collection of attributes that does **not** have a distinct identity or primary key. It represents a descriptive value bound directly inside its parent record.
* **Engine Behaviors Generated:**
* Inlined directly into the parent database table (JSON column or flattened column prefixes like `address_street`, `address_city`).
* Replaced entirely during updates rather than mutated partially.
* Deleting the parent automatically deletes the embedded value object data.


* **Concrete Example:** `GeoCoordinates` or `NotificationPreferences`
* *Why:* A GPS coordinate (`latitude: 38.8951`, `longitude: -77.0364`) or a preferences block (`marketing_opt_in: true`, `preferred_language: "en-US"`) isn't an independent entity with its own database ID. It is simply a structured value describing the parent entity.



---

### **4. `RefDataEntity` (Reference / Reference Data)**

* **What it indicates:** A system-wide or domain-wide lookup code, standardized classification, or taxonomy. These entities are typically managed by administrators, heavily cached, and read-heavy.
* **Engine Behaviors Generated:**
* Read-only public APIs and aggressively cached repositories (in-memory / Redis).
* Enforces strict Foreign Key constraints from operational entities to prevent linking to invalid classification codes.


* **Concrete Example:** `ServiceTechnologyType` (Telecom) or `CountryCode` (Global)
* *Why:* Standard values like `FTTH` (Fiber to the Home), `5G_NSA`, or `DOCSIS_3_1` are managed centrally. Operational entities like `ServiceableLocation` reference these codes, but operational users do not create or delete them during normal application workflows.



---

### **5. `TransactionEventEntity` (Append-Only / Immutable Ledger)**

* **What it indicates:** An immutable event record representing something that occurred at a specific point in time. Once written, these records are strictly read-only and cannot be updated or deleted by standard business logic.
* **Engine Behaviors Generated:**
* Emits append-only repositories (disallows `UPDATE` or `DELETE` operations at the service layer).
* Automatically injects precision timestamping, sequence numbers, and immutable audit metadata.


* **Concrete Example:** `BillingChargeEvent` or `StatusTransitionLog`
* *Why:* When a subscriber is charged $79.99 or their status moves from `Active` to `Suspended`, that historical record must remain pristine for accounting and legal audit trails.



---

### **Summary Classification Matrix**

| `type` Value | Primary Key? | Lifecycle Bound to Parent? | Default DB Deletion Behavior | Primary Use Case |
| --- | --- | --- | --- | --- |
| **`IndependentEntity`** | Yes (Autonomous) | No (Persists independently) | `ON DELETE SET NULL` / Soft Decouple | Core domain entities (`ServiceableLocation`, `User`) |
| **`DependentEntity`** | Yes | Yes (Owned by parent) | `ON DELETE CASCADE` | Parent-owned sub-resources (`TroubleTicket`, `DeviceBinding`) |
| **`EmbeddedValueObject`** | No | Yes (Inlined in parent) | Inline deletion with parent | Structured attributes (`GeoCoordinates`, `Preferences`) |
| **`RefDataEntity`** | Yes (Code/ID) | No (Global read-only) | Restrict Deletion | Taxonomies, lookup tables (`ServiceTechnologyType`) |
| **`TransactionEventEntity`** | Yes | No (Append-only) | Disallowed (`UPDATE`/`DELETE` blocked) | Financial transactions, state change audit logs |

You have pinpointed a fundamental requirement for enterprise systems: **the difference between structural/data deletion and business lifecycle termination**.

In enterprise domain models—especially in telecom, finance, and subscription platforms—we almost never perform a physical `DELETE` or even a simple hard cascade. Instead, business events trigger **Logical Lifecycle Transitions** (such as `Deactivate`, `Suspend`, `Terminate`, or `Disconnect`) where records enter an inactive state with effective start/end timestamps.

When a customer reconnects, the framework should support **Lifecycle Resumption / Re-activation** cleanly without recreating past data or corrupting historical audit logs.

Here is how we refine the entity pattern and engine behaviors to support this natively.

---

### **1. The Pattern: `StatefulLifecycleEntity**`

Instead of relying on database-level `ON DELETE CASCADE`, we introduce an explicit lifecycle pattern for `DependentEntity` (and optionally `IndependentEntity`): **`StatefulLifecycleEntity`**.

This pattern replaces physical deletion with an **Effective-Dated State Machine**.

#### **Core Standard Attributes (Auto-Injected by `meta_builder_brain`)**

When an entity is typed or tagged as `StatefulLifecycle`:

* **`lifecycle_state`:** Choice (`Active`, `Pending_Disconnect`, `Disconnected`, `Suspended`, `Archived`).
* **`effective_start_date`:** Timestamp (When the current state became active).
* **`effective_end_date`:** Optional Timestamp (Populated when disconnected/terminated).
* **`termination_reason`:** Optional Choice (`Customer_Request`, `Non_Payment`, `Location_Move`, `Upgrade`).

---

### **2. Operations & Transitions: Disconnect vs. Reconnect (Resubscribe)**

`meta_polymorph` and `meta_compiler` generate two distinct operational flows for these entities rather than standard CRUD `destroy()` methods:

```
                  ┌────────────────────────┐
                  │        ACTIVE          │
                  └───────────┬────────────┘
                              │
                    Action: Disconnect
                    (Set end_date = now)
                              │
                              ▼
                  ┌────────────────────────┐
                  │      DISCONNECTED      │
                  └───────────┬────────────┘
                              │
                    Action: Reconnect / Resume
                    (Evaluate window & transition)
                              │
         ┌────────────────────┴────────────────────┐
         │                                         │
   Within Grace Period                      Grace Period Expired
   (e.g., < 30 Days)                        (e.g., > 30 Days)
         │                                         │
         ▼                                         ▼
┌────────────────────────┐              ┌────────────────────────┐
│ REACTIVATE EXISTING    │              │ CLONE & START NEW      │
│ (Clear end_date, reset │              │ (Keep old log closed,  │
│ state to Active)       │              │ create fresh instance) │
└────────────────────────┘              └────────────────────────┘

```

#### **A. Disconnect Flow (Cascading Logical Termination)**

When a parent `Customer` or `Account` is disconnected:

1. The parent triggers a **Cascade Deactivation Event** (not a SQL `DELETE`).
2. All linked child services/products transition to `Disconnected`.
3. `effective_end_date` is stamped with the disconnection timestamp.
4. Physical database rows remain completely intact for historical reporting, billing reconciliation, and regulatory compliance.

#### **B. Reconnect / Resubscribe Flow (Grace Period Handling)**

When a customer reconnects, `meta_builder_brain` enforces one of two configurable business policies based on the time elapsed:

1. **Reactivation (Within Grace Period - e.g., 7–30 days):**
* The existing product record is **un-archived**.
* `lifecycle_state` reverts to `Active`.
* `effective_end_date` is cleared (`NULL`).
* *Result:* Preserves history, original configuration, equipment bindings, and identifiers without generating duplicate clutter.


2. **Re-issuance (After Grace Period):**
* The old record remains closed (`Disconnected` with past end date).
* A **new** active product instance is created, linking back to the historical lineage if necessary.

### **3. Catalog Schema Representation**

Here is how this capability is declared declaratively in the **Industry Catalog Schema**:

```yaml
catalog_urn: urn:meta:industry:telecom:entities:CustomerService:v1
type: DependentEntity
traits:
  - StatefulLifecycle # Signals effective dating and soft-state engine rules

lifecycle_config:
  initial_state: Active
  states: [Active, Pending_Disconnect, Disconnected, Suspended]

  # Business rules for disconnection and resumption
  disconnection_policy:
    cascade_from_parent: true # Parent disconnect triggers service disconnect
    action: MarkDisconnected  # NEVER physical delete

  resumption_policy:
    allow_reactivation: true
    reactivation_grace_period_days: 30 # Reconnect within 30 days re-uses record
    on_reactivate_action: ClearEndDateAndActivate

```

### **4. How `meta_*` Engine Implements This**

* **`meta_builder_brain`:** Detects the `StatefulLifecycle` trait. Automatically injects state-transition rules, `effective_start_date`, and `effective_end_date` into the domain model graph without requiring the developer to declare them manually.
* **`meta_polymorph`:** Replaces generated `repository.delete()` interface methods with `service.disconnect()` and `service.reconnect()` state-transition contracts. * **`meta_compiler`:** Emits state-machine transition code in `service.py` along with unit/integration tests verifying that:
* Disconnecting sets `effective_end_date`.
* Reconnecting within 7 days restores the same record to `Active`.
* Data is never physically purged during service teardown.

Rather than treating state management as ad-hoc string fields or manual status updates, the compiler treats the lifecycle as a formal **State Machine**.

---

### **1. How the State Transition Engine Is Modeled**

When an entity includes the `StatefulLifecycle` trait in the catalog or spec, `meta_builder_brain` models a structured transition matrix:

```yaml
# Internal Model Constructed by meta_builder_brain
lifecycle_matrix:
  entity: CustomerService
  states: [Pending, Active, Suspended, Pending_Disconnect, Disconnected]
  initial: Pending

  transitions:
    - name: activate
      from: [Pending, Suspended, Disconnected]
      to: Active
      guard: validate_billing_standing
      effects: [clear_end_date, emit_activation_event]

    - name: suspend
      from: [Active]
      to: Suspended
      effects: [stamp_suspension_reason]

    - name: disconnect
      from: [Active, Suspended]
      to: Disconnected
      effects: [stamp_end_date_now, trigger_child_cascade_disconnect]

```

---

### **2. Code Generated by `meta_compiler**`

When compiling the module, `meta_compiler` generates the following concrete layers based on that transition matrix:

#### **A. Strongly Typed State Handlers (`service.py`)**

* Emits explicit, type-safe transition methods (e.g., `disconnect_service()`, `reactivate_service()`) rather than generic update operations.
* Validates allowed transitions. If an invalid transition is attempted (e.g., moving directly from `Pending` to `Disconnected` without activation), it raises a generated `InvalidStateTransitionError`.
* Executes guards and effects (such as stamping `effective_end_date = datetime.now(timezone.utc)` or evaluating the **Reactivation Grace Period** logic).

#### **B. Automatic Cascade Interceptors**

* Parent state changes trigger logical downstream events. Disconnecting a `Customer` automatically emits internal dispatch calls to execute `disconnect_service()` across all linked `DependentEntity` records.

#### **C. Query Scope Filters (`repository.py`)**

* Generates active vs. historical query contracts automatically:
* `find_active()` $\rightarrow$ Queries records where `lifecycle_state = 'Active'` and `effective_end_date IS NULL`.
* `find_historical()` $\rightarrow$ Queries full effective-dated timeline including past `Disconnected` states for audit and reconnect evaluations.



#### **D. State Transition Verification Tests (`test_unit.py` / `test_integration.py`)**

The compiler automatically generates test suites covering:

* Valid state transitions (e.g., `Active` $\rightarrow$ `Disconnected`).
* Invalid state transition blocks (e.g., attempting illegal state jumps).
* Grace-period resumption logic (verifying that reconnecting within the window restores the existing record while reconnecting outside the window generates a new instance).

---

---

#### **Python State Machine Libraries**

If the compiled application runs as a lightweight standard Python microservice (FastAPI, Pydantic, SQLAlchemy):

* **`python-statemachine` / `transitions`:**
* **What they do:** Provide in-memory finite state machines (FSM), guard validations, transition callbacks, and state-change hooks.
* **`meta_builder` Binding Strategy:** `meta_compiler` generates a standard `statemachine.StateMachine` class definition directly into `models.py` or `service.py`. The generated `disconnect()` or `activate()` methods simply trigger framework callbacks rather than manual `if/else` checks.

For long-running enterprise lifecycles (e.g., a disconnection order that waits 30 days for return of equipment before moving to `Archived`):

* **Temporal.io / Cadence:**
* **What they do:** Guarantee durable state execution, timer handling, grace-period waits, and deterministic event-driven state transitions across microservices.


* **Apache Hamilton / NetworkX:**
* **What they do:** Execute directed acyclic graph (DAG) dependencies and data-flow pipelines cleanly.

```python
from statemachine import StateMachine, State

class ServiceLifecycleFSM(StateMachine):
    # States
    pending = State('Pending', initial=True)
    active = State('Active')
    suspended = State('Suspended')
    disconnected = State('Disconnected')

    # Transitions
    activate = pending.to(active) | suspended.to(active) | disconnected.to(active)
    suspend = active.to(suspended)
    disconnect = active.to(disconnected) | suspended.to(disconnected)

    def on_enter_disconnected(self, model):
        # Auto-generated effect derived from 'StatefulLifecycle' trait
        model.effective_end_date = datetime.now(timezone.utc)

```

**Requirements Specification Update: Dual-Track Execution Model**

This update formalizes the **Dual-Track Execution Model** within the `meta_builder` architecture. It establishes how generated applications handle immediate synchronous state transitions alongside multi-week, asynchronous operational workflows.

---

### **1. Architectural Concept**

To support enterprise lifecycle operations without coupling fast API responses to long-running operational checks, `meta_builder` routes business events through two distinct execution tracks based on event semantics defined in the Domain Entity Template (DET) or Industry Catalog.

```
                                  ┌────────────────────────┐
                                  │ Incoming Domain Event  │
                                  └───────────┬────────────┘
                                              │
                       ┌──────────────────────┴──────────────────────┐
                       │                                             │
                       ▼                                             ▼
         [ExecutionMode: Synchronous]                 [ExecutionMode: Workflow]
                       │                                             │
                       ▼                                             ▼
        ┌──────────────────────────────┐              ┌──────────────────────────────┐
        │  Synchronous FSM Engine      │              │  Durable Workflow Engine     │
        │  (e.g., python-statemachine) │              │  (e.g., Temporal.io SDK)     │
        ├──────────────────────────────┤              ├──────────────────────────────┤
        │ • Microsecond DB transactions│              │ • Asynchronous execution     │
        │ • Direct API response        │              │ • Durable timers (days/weeks)│
        │ • Real-time status flips     │              │ • Field technician dispatches│
        │ • In-memory validation guards│              │ • Compensating signals       │
        └──────────────────────────────┘              └──────────────────────────────┘

```

---

### **2. Execution Track Specifications**

#### **Track A: Synchronous State Machine (Immediate Execution)**

* **Target Scenarios:** Real-time business events requiring immediate resolution (e.g., payment receipt clearing a non-payment suspension, customer changing profile details, real-time feature toggle).
* **Runtime Binding Target:** `python-statemachine` integrated with standard ORM (`SQLAlchemy`/`Pydantic`).
* **Engine Behavior:**
* Executes in-thread within a single ACID database transaction.
* Evaluates state guards instantly (e.g., checking account balance before clearing suspension).
* Mutates `lifecycle_state` and returns immediate success/failure HTTP or gRPC responses.



#### **Track B: Asynchronous Durable Workflow (Long-Running Operations)**

* **Target Scenarios:** Multi-step operational processes involving human intervention, external system dependencies, or physical dispatches (e.g., scheduling a technician truck roll, 30-day equipment return grace periods, multi-stage disconnect orders).
* **Runtime Binding Target:** `Temporal.io` Python SDK (or Cadence/Airflow depending on compiler target).
* **Engine Behavior:**
* Dispatches non-blocking, event-driven workflows.
* Handles durable execution state: process execution can pause for hours, days, or weeks without consuming CPU or memory resources.
* Supports **External Cancellation Signals**: If a real-time event (e.g., `PaymentReceived`) occurs while an asynchronous workflow (e.g., `ScheduledDisconnectDispatch`) is pending, the synchronous track emits an external signal to cancel the pending workflow and execute compensating activities.



---

### **3. Catalog Schema Specification (`execution_mode`)**

Lifecycle events in the Industry Catalog or Provider Spec explicitly declare their execution strategy:

```yaml

traits: [StatefulLifecycle]

lifecycle_events:
  # TRACK A: Immediate Real-Time Transition

    trigger_from: Suspended_NonPayment
    target_state: Active
    execution_mode: Synchronous
    actions:
      - ClearOutstandingBalance
      - SignalCancelPendingDisconnections  # Inter-track signal

  # TRACK B: Long-Running Operational Process
  - event: ScheduleServiceTermination
    trigger_from: [Active, Suspended_NonPayment]
    target_state: Pending_Field_Dispatch
    execution_mode: Workflow
    workflow_definition:
      steps:
        - ScheduleTruckRoll:
            appointment_window_days: 14
        - AwaitFieldTechnicianCompletion:
            timeout: "21_days"
        - TransitionToState: Disconnected
      compensations:
        on_signal_cancel:
          - CancelTruckRollOrder
          - TransitionToState: Active

```

---

### **4. Component Responsibilities for Dual-Track Model**

* **`meta_builder_brain`:** Inspects event definitions, determines track routing (`Synchronous` vs. `Workflow`), builds state-transition matrices, and links cancellation signals between synchronous mutators and asynchronous workflow steps.
* **`meta_polymorph`:** Generates distinct service layer signatures: direct execution methods for synchronous events and workflow starters/signal emitters for long-running processes.
* **`meta_compiler`:** Generates two co-existing module components:
* `service.py`: Contains standard REST/gRPC endpoints backed by `python-statemachine`.
* `workflows.py`: Contains Temporal workflow and activity definitions managing timers, field checks, and compensation handlers.
* `test_unit.py` / `test_integration.py`: Tests both immediate state flips and simulated workflow executions (using Temporal test environments).
